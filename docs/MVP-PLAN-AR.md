# خطة منصة الخدمات الطبية المنزلية

## ١. خريطة الموقع

| المسار | الشاشة | الوصول |
|---|---|---|
| /login | الدخول بالبريد أو واتساب | عام |
| /verify | التحقق من الرمز أو الرابط | جلسة تحقق مؤقتة |
| /profile | الاسم والهاتف والعنوان | المريض |
| /services/request | طلب خدمة واختيار جنس الكادر | المريض |

هذه مسارات مستهدفة؛ إضافة صفحة /login هي مرحلة التنفيذ الأولى. المشروع الحالي يحتوي على رحلة تمريض تجريبية مستقلة، وليست مصادقة إنتاجية.

## ٢. مخطط قاعدة البيانات المقترح

يُحافظ على PostgreSQL وPrisma الموجودين. المخطط التالي اقتراح للمرحلة الجديدة وليس ترحيلاً منفذاً على قاعدة البيانات.

| الجدول | الحقول الأساسية |
|---|---|
| users | id UUID، auth_subject unique، role patient/admin، name، phone، email، address، created_at |
| services | id، name، active، created_at |
| providers | id، name، phone_e164، gender، active |
| provider_services | provider_id + service_id مفتاح مركب |
| requests | id، patient_id، kind medical/pharmacy، service_id nullable، service_name_snapshot، applicant_name، phone، address، details، staff_preference، medicine_name nullable، status pending/forwarded/completed، created_at |
| attachments | id، request_id، private_object_key، mime_type، size_bytes، created_at |
| assignments | id، request_id، provider_id، created_by، forwarded_at، accepted_at nullable |
| payments | id، request_id unique، provider_id، service_name_snapshot، amount nullable decimal، currency، status paid، paid_at، recorded_by |
| site_settings | id singleton، site_name، brand_name، logo_key nullable، updated_at |
| audit_events | id، actor_id، entity_type، entity_id، action، created_at |

العلاقات: مستخدم واحد له طلبات متعددة؛ الطلب له مرفقات وتحويلات متعددة وقيد دفع واحد؛ مقدم الخدمة يرتبط بخدمات متعددة. يمنع المبلغ السالب، ويُسجل الدفع والتحويل داخل معاملات. فتح واتساب لا يعني قبول مقدم الخدمة أو حدوث دفع؛ التأكيد يسجله المدير صراحة. يستخدم تاريخ الطلب في فلترة الحسابات، مع فهرسة requests.created_at وpayments.provider_id.

تعطيل الخدمات ومقدمي الخدمة المستخدمين في سجلات سابقة يحافظ على التاريخ. حذف غير المستخدمين ممكن. تحفظ أسماء الخدمة وبيانات الاتصال وقت الطلب حتى لا تغير التعديلات السجلات القديمة.

## الصلاحيات والتكامل

- تفرض صلاحية المدير على الخادم؛ لا يُقبل الدور من المتصفح. المريض يقرأ طلباته فقط.
- المرفقات خاصة بروابط مؤقتة بعد فحص الملكية؛ تحقق من نوع الملف الفعلي وحجمه، إزالة EXIF وضغط الصور وإعادة ترميزها على الخادم.
- يستخدم مزود مصادقة مُدار للبريد، ومزوّد WhatsApp Business مع قالب تحقق معتمد لواتساب. روابط wa.me لا ترسل رموز OTP.
- رموز قصيرة العمر، أحادية الاستعمال، مع حد لمحاولات الإرسال والتحقق ورسائل لا تكشف وجود الحساب. جلسات HttpOnly وSecure وSameSite، وحماية CSRF.
- لا تحفظ بيانات المرضى أو الوصفات في localStorage، ولا تكتب الرموز أو التفاصيل الطبية في السجلات.
- مشاركة الطلب عبر واتساب تكون بفعل المدير، مع الحد الأدنى من البيانات وإبلاغ المريض بكيفية مشاركة بيانات طلبه.

## ٣. ترتيب التطوير

1. صفحة الدخول: واجهة RTL والتحقق من المدخلات، ثم ربط مزود مصادقة حقيقي واختبار الجلسات.
2. الملف الشخصي وطلب الخدمة مع قائمة خدمات من قاعدة البيانات.
3. الصيدلية والتخزين الخاص للمرفقات.
4. لوحة المدير والتحويل وإدارة الخدمات والمقدمين والعلامة.
5. الحسابات والبحث وفلترة التاريخ ومقدم الخدمة.
6. اختبارات الصلاحيات والرفع والجوال والحركات المخفضة، ثم إعداد النشر.

تتطلب المرحلة الإنتاجية بيانات إعداد مزود المصادقة وقاعدة البيانات والتخزين الخاص. لا تمنح صفحة الدخول الجديدة وصولاً إلى بيانات حقيقية قبل إتمام ربط الجلسات.
